# AI Media UI 改版计划

> 本文为 UI 目标方案，已开始分阶段实施；实际完成情况及限制见 `docs/当前功能.md`，不代表全部功能已经实现。

## 方案速览（先看这里）

- 定位：一个以对话为入口的文章工作台，围绕“求实、改稿、配图、发布”，不做复杂运营后台。
- 导航：只保留“文章、Skills、发布记录、设置”四项。
- 主界面：正文居中、Agent 对话在右，来源和版本在左；窗口变小时先收起资料，再切换正文与对话，不挤压阅读空间。
- 确认方式：改稿先看差异；图片先确认 prompt、生成后选择插入；发布先核对平台、账号和最终内容。
- 视觉：以根目录 `design.md` 的 Studio 规范为准，改用钴蓝与冷灰白 / 石墨黑，统一主题和动效。
- 开发：复用现有编辑器、对话、审批和主题组件，遵守 `AGENTS.md` 的 Ponytail 约束，不另起一套 UI。

建议顺序：确认本方案 → 工作区关键状态原型 → 改稿与求实 → Skills → 配图 → 首个平台浏览器发布 → 全流程验收。

原型先覆盖“正常编辑、修改待确认、图片待确认、发布待确认、异常接管”五种状态；验证宽屏与窄屏后再实施。首个发布平台已确定为微信公众号。

## 1. 改版目标

围绕“对话改稿 → 求实 → 配图 → 浏览器发布”，完善对话式文章工作台，不扩展成通用内容后台。

用户进入文章后，应当始终看见三件事：

1. 正在修改的文章。
2. 与 Agent 的对话和执行进度。
3. 搜索来源、修改差异、图片或发布等待确认的内容。

当前已有四项导航、自适应工作区、改稿差异与版本保护、逐条事实结论、Skills 执行展示、图片结果选择和微信公众号模拟发布。四个主页面的窄屏、深色、键盘焦点、文字对比度与 200% 缩放已完成自动验收；后续重点是真实 Firecrawl 质量、真实辅助技术和已登录公众号页面验收。浏览器登录窗口本身不等于真实发布已经验收。

## 2. 新的信息架构

主导航只保留四项：

```text
文章
Skills
发布记录
设置
```

- “模板管理”并入 Skills。
- “账号”并入发布设置。
- “任务”统一改称“文章”。
- 统计卡片、批量模板调试和 Webhook 配置不再占据主流程。

## 3. 核心页面方案

### 3.1 文章列表

页面只解决选择和创建文章：

- 搜索文章。
- 新建或导入文章。
- 显示标题、来源、最近修改时间和当前状态。
- 分别显示编辑状态与发布状态，例如“待审阅 · 未发布”；不把“改稿完成”误写成“已发布”。
- 点击文章进入工作区。

不再用大面积统计卡片抢占首屏。

### 3.2 文章工作区

宽屏采用三栏结构，进入工作区后主导航可收起为窄栏，留出正文空间：

```text
┌──────────────┬──────────────────────────┬──────────────────┐
│ 来源 / 版本   │ 文章编辑器与预览          │ Agent 对话         │
│              │                          │                  │
│ 求实来源      │ 标题                     │ 消息              │
│ 事实结论      │ 正文                     │ 工具执行进度       │
│ 历史版本      │ 图片与视频               │ 审批卡片           │
│              │                          │ 输入框            │
└──────────────┴──────────────────────────┴──────────────────┘
```

- 左栏：来源、事实核查和历史版本，可折叠。
- 中栏：文章正文，是页面视觉中心；“编辑 / 修改对比”在同一区域切换，不把两篇完整文章上下堆叠。
- 右栏：Agent 对话，双栏和三栏布局下常驻；窄屏通过标签切换。
- 顶部：文章标题、保存状态、保存和发布按钮；Skill 选择器放在对话输入区，不重复展示。
- Agent 运行时显示当前步骤，但不遮挡正文编辑。
- 对话可以提出改稿、配图或准备发布；识别要求时显示文字模型进度。多个动作或不明确的要求先澄清，不擅自串行执行。识别动作不能代替审批，配图与发布复用现有确认卡。

布局建议：

- ≥1440px：资料约 220px，正文自适应，对话约 360px，栏间距 16px。
- 1100–1439px：正文与对话双栏，资料改为抽屉。
- <1100px：正文与对话使用标签切换，资料仍为抽屉；待确认事项显示数量并可直达。
- 切换面板保留输入和滚动位置；不靠整页横向滚动容纳三栏。

### 3.3 Skills 页面

- 分为“内置”和“已安装”两个列表。
- 每个 Skill 显示名称、用途、来源、版本、状态和所需权限。
- 支持安装、启用、停用、更新、卸载。
- 点击后展示说明和适用场景，不直接暴露复杂文件结构。
- 文章工作区通过 Skill 选择器查看或指定本轮使用的 Skills；配图自动匹配声明图片能力的 Skill，仍在同一执行记录中显示，不能跳过提示词确认。

### 3.4 发布记录

- 显示文章、平台、账号、状态、执行时间和失败原因。
- 可查看浏览器执行步骤。
- 失败项支持重试或重新接管。
- 平台账号和浏览器登录状态放入本页设置抽屉，不单独占一个主导航。

### 3.5 设置

按能力分组：

- Agent 与文字模型。
- Firecrawl 搜索。
- 图片模型。
- 浏览器与发布。
- 数据与应用。

## 4. 三条关键交互

### 4.1 求实与改稿

```text
用户提出修改要求
→ Agent 搜索并显示进度
→ 左栏出现来源和事实结论
→ 中栏显示修改差异
→ 用户接受、拒绝或继续对话
```

来源必须能打开。事实结论区分“来源支持、证据反驳、存在争议、无法确认”，说明依据，不把模型判断展示成绝对真相。

- 结论关联具体原文、证据和核查时间；搜索命中不等于事实已证实，不给没有依据的“准确率”。
- 差异标明新增、删除和替换，并附简短修改说明；第一版支持整轮接受或拒绝，逐段接受后续再做。
- 等待确认时可直接输入新的改稿要求，基于候选稿生成替代版本；新一轮失败时恢复上一版候选稿，接受前始终不写入正文。配图或发布仍需先处理当前候选稿。
- 改稿以用户发送时的正文为基准。用户之后又编辑了文章时，接受前提示冲突，不能覆盖新内容。
- 没有来源、工具失败、生成中和等待确认都有明确反馈，不能只显示空白或无限转圈。

### 4.2 文章配图

```text
用户提出配图需求
→ Agent 生成可编辑的 prompt 卡片
→ 用户确认
→ 执行文生图或图生图
→ 用户选择结果并插入文章
```

确认卡展示 prompt、文生图/图生图模式、画幅和参考图。确认前不调用图片模型；生成后先展示结果，不自动插入正文。重新生成复用同一张任务卡片，每次产生新费用前再次确认。

### 4.3 浏览器发布

```text
用户点击发布
→ 选择平台和账号
→ Agent 打开浏览器并填写内容
→ 展示发布预览
→ 用户确认
→ 点击真实发布并记录结果
```

遇到登录、验证码或页面异常，状态切换为“需要接管”，并提供打开浏览器按钮。

最终确认展示平台、账号、标题、正文和图片；其中任何内容变化都使旧确认失效。结果不明时只显示“核对发布结果”，禁止直接重填或用取消绕过核对。用户在公众号发表记录中核对后，明确选择“已发布”或“未发布”；人工核对记录不能冒充自动成功证据，确认未发布也不能自动重发。发布成功应有平台结果页等可核对凭据。未支持的平台明确标注，不展示可用的发布按钮。

## 5. 共用组件

优先复用现有组件，以下是职责划分，不要求每行都新建一个文件：

| 组件 | 用途 |
| --- | --- |
| `AppShell` | 主导航、标题栏和全局状态 |
| `ArticleList` | 文章搜索、筛选和选择 |
| `RichEditor` | 复用现有正文编辑和媒体内容能力 |
| `AgentPanel` | 对话、输入和运行状态 |
| `ToolActivity` | 搜索、Skill、图片和浏览器工具进度 |
| `ApprovalCard` | 修改、图片和发布的统一确认容器 |
| `DiffReview` | 接受或拒绝文章修改 |
| `EvidencePanel` | 事实结论和来源列表 |
| `SourceCard` | 来源标题、站点、摘要和链接 |
| `SkillCard` | Skill 信息、状态和操作 |
| `MediaPreview` | 上传图、生成图和图生图结果 |
| `RunTimeline` | Agent 与发布执行过程 |
| `StatusBadge` | 全局统一状态显示 |

只有发生真实复用时才继续拆分，不为单个页面创建多层包装组件。

按 [DietrichGebert/ponytail](https://github.com/DietrichGebert/ponytail) 的最小实现原则：先确认必要性，再查已有实现、标准能力、平台原生能力和已安装依赖，最后才写新代码。沿用现有 React、Tiptap、基础控件和主题，不为改版另装一套 UI 框架；页面只组合组件，业务逻辑留在对应模块。不省略数据保护、校验和可访问性。

## 6. 状态模型

Agent、图片和发布流程共用以下状态：

- `idle`：未开始。
- `running`：执行中。
- `awaiting_approval`：等待用户确认。
- `needs_handoff`：需要用户接管。
- `completed`：完成。
- `failed`：失败。
- `cancelled`：已取消。

共用状态字段和展示组件，但保留各流程的合法转换规则；文章保存、审批决定和发布结果分别记录，不用一个状态覆盖所有事情。审批和权限必须由服务端执行校验，不能只靠前端禁用按钮。

## 7. 视觉方向

- 2026-09-05 起，色号、动效、样式与组件契约统一在根目录 `design.md` 维护，替代青绿与暖灰方案。以下仅保留阅读与流程原则。
- 文章区域保持接近纸张的阅读体验，控制正文宽度。
- Agent 区使用轻边界，不与文章争夺视觉焦点。
- 蓝色表示来源，橙色表示待确认，绿色表示成功，红色只表示失败或风险。
- 深色模式继续保留。
- 正文、按钮和状态颜色满足 WCAG AA；所有核心操作支持键盘和清晰焦点状态。
- 动效只用于流式生成、状态切换和面板展开，并支持减少动态效果设置。

视觉落地规格与验收矩阵见 `design.md`；弹层关闭后焦点回到原按钮，缩放到 200% 时仍可完成核心操作。旧版截图与布局测试不能替代新版验收。

## 8. 实施阶段

### 方案确认：先审界面，再改代码

- 先确认本文件的页面结构、视觉方向和关键确认流程。
- 基于现有组件制作工作区关键状态原型，不连接真实生图或发布操作。
- 验收：用户能清楚分辨当前正文、候选修改、证据和待确认动作；窄屏也能完成相同操作。
- 确认后按以下阶段推进，已有能力只做必要调整和回归检查，不重复建设。

### 阶段一：工作区布局与基础组件

- 在现有四项导航和工作区上调整布局，不重新建一套页面。
- 统一主题、字号、状态和确认卡，完成宽屏、双栏与窄屏切换。
- 复用现有编辑器、版本和媒体能力，保留未保存内容。
- 验收：不同窗口宽度下都能编辑、对话、查看资料和处理确认，无横向溢出。

### 阶段二：Agent 改稿

- 完善对话进度与 Firecrawl 事实结论，关联原文和来源。
- 补齐修改差异、接受、拒绝和版本冲突保护。
- 验收：基于当前正文改稿，拒绝不改正文，接受不覆盖后续编辑，失败不丢稿。

### 阶段三：Skills

- 完善已有 Skills 页面：安装、启停、更新、卸载和权限预览。
- 补齐独立目录、参考资料加载，以及自动匹配和明确指定。
- 验收：执行记录可见所用 Skills；更新不覆盖用户内容，停用的 Skill 不执行。

### 阶段四：图片

- 完善已有 prompt 卡片，加入参考图预览和生成结果选择。
- 打通文生图、图生图、重新生成和用户选择后插入文章。
- 验收：未确认不生图，确认前取消不消耗生成额度，失败可再次确认后重试；已提交模型后的费用如实提示。

### 阶段五：浏览器发布

- 首个发布平台为微信公众号，建立对应 adapter 和浏览器运行状态；不改变最终确认和安全接管要求。
- 完成发布预览、确认、接管、结果记录和安全重试。
- 验收：用一个真实平台走完整条链路；未确认不发布，异常可接管，重试不重复发布。

### 阶段六：清理旧功能

- 确认新流程验收通过后，再清理被替代的重复页面和组件，保留用户数据。
- 仅在确认仍需兼容时保留 Webhook 与旧数据迁移。
- 完成桌面端完整流程和可访问性验收。

## 9. 第一版验收范围

第一版先打通一条完整链路：

1. 导入或新建文章。
2. 与 Agent 对话并通过 Firecrawl 核实内容。
3. 查看来源，接受一版文章修改。
4. 确认 prompt 后生成一张图片并插入文章。
5. 使用一个目标平台完成浏览器发布。

此外必须验收一次图生图和一次用户 Skill 安装与调用。覆盖确认、拒绝、失败、重试和浏览器接管；检查浅色/深色、窄屏、键盘操作和重启后的数据保留。

这条链路稳定后，再增加更多内置 Skills 和发布平台。暂不做统计大屏、批量运营、复杂定时策略或独立 Skill 商城。
